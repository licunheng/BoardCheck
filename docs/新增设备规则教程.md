# 新增设备规则教程(开发者)

> 适用对象:负责板检上位机/数据上报的开发者。
> 阅读时间: 10 分钟。
> 目标:让一个新设备(如 B05WX)的板检数据能够被本工具核验。

---

## 一、整体流程

```
复制模板
   ↓
填写 4 个配置文件
   ↓
放入 1~3 个真实样本
   ↓
跑规则自检
   ↓
通过 → 上线使用
不通过 → 调整规则 → 重跑自检
```

---

## 二、详细步骤

### 1. 复制模板目录

```bash
cp -r agent/devices/_template agent/devices/<新设备型号>
cd agent/devices/<新设备型号>
```

### 2. 填写 `device.json`(设备身份卡)

打开 `device.json`,把占位符替换为真实值。

关键字段:

```json
{
  "device_code": "B05WX",                  // 设备型号,英文/数字
  "display_name": "B05WX 5G 网关",         // 显示名,中文
  "is_4g": true,                            // 是否 4G/5G 设备(决定是否校验 ICCID)

  "platform_csv_columns": {
    "sn": "设备序列号",        // 平台 CSV 中 SN 的列名
    "trace_code": "追溯码",
    "mac": "MAC地址",
    "iccid": "ICCID"
  },

  "field_definitions": {
    "sn": {
      "pattern_in_raw": "<SN 的正则>",
      "example": "<示例 SN 值>"
    },
    ...
  }
}
```

### 3. 填写 `filter_rules.json`(行级过滤)

打开 `filter_rules.json`,列出该设备日志的过滤规则。

**先做正向思考** — 什么样的行必须保留?

| 保留 (keep_patterns) | 剔除 (drop_patterns) |
|---|---|
| 含 SN/MAC/ICCID/追溯码的关键行 | DEBUG/INFO/版本信息行 |
| 测试步骤行 | 重试/超时行 |
| | 板检启动/结束行 |

格式:标准正则字符串。

### 4. 填写 `extraction_rules.json`(字段抽取)

打开 `extraction_rules.json`,为每个字段写精确正则。

**黄金法则**:正则越精确越好,宁可漏几条也不要错配。

例:

```json
{
  "field_extractors": {
    "sn": {
      "regex": "SN=([A-Z0-9]{32})",       // 必须精确匹配 SN 的真实格式
      "context_anchor": "板检命令:.*?SN=([A-Z0-9]{32})",  // 可选,二次校验
      "post_process": ["trim", "upper"],
      "must_be_present": true,
      "notes": "SN 必须从测试命令里抽取,不能从设备回复里抽取"
    }
  }
}
```

### 5. 填写 `prompts.md`(LLM 兜底提示)

打开 `prompts.md`,用自然语言描述:
- 该设备的核心特征
- 字段抽取的"陷阱"(LLM 容易犯的错误)
- 一个完整测试循环由哪几行构成

这部分仅在 LLM 兜底时生效。

### 6. 放入样本

把 1~3 个真实样本文件复制到 `samples/` 目录:

```
samples/
├── 2026-08-04.txt        # 板检日志样本
├── 2026-08-04.csv        # 对应平台 CSV(可选)
└── README.md             # 标注样本来源、日期、说明
```

### 7. 跑规则自检

```bash
# 开发模式
python3 -m agent --device B05WX --rule-check

# 打包后 EXE 模式
板检数据核验Agent.exe --device B05WX --rule-check
```

自检输出:
```
━━━ 设备规则自检报告: B05WX ━━━

样本文件: 1 个
  - 2026-08-04.txt

文本日志输入行数: 1234
过滤后保留行数: 567
行保留率: 45.95%
抽取到设备记录: 50 条

字段抽取统计:
  字段             总数      抽取到     缺失      成功率
  sn             50       48      2    96.0%
  mac            50       50      0   100.0%
  iccid          50       50      0   100.0%

✅ 自检通过
```

## 三、规则调整技巧

### 技巧 1: 行保留率过低(<10%)

说明 `drop_patterns` 漏配或 `keep_patterns` 写得太严。

调试:
```bash
# 查看具体哪些行被剔除
python3 -c "
from agent.core.preprocessor import _should_drop
from agent.core.rule_loader import DeviceRules
rules = DeviceRules.load('B05WX')
with open('samples/2026-08-04.txt', encoding='utf-8') as f:
    for i, line in enumerate(f, 1):
        if _should_drop(line, rules):
            print(f'{i}: {line.rstrip()[:100]}')
" | head -20
```

### 技巧 2: 字段成功率 < 90%

说明正则不精确。常见原因:
- **格式变了**:你的正则假设了固定位数,但实际有变化
- **位置错了**:SN 可能在不同位置,需要更宽松的锚点
- **大小写不一致**:加 `re.IGNORECASE` 或 post_process 用 `upper`

### 技巧 3: 多个串口并行测试

A02FG 案例:COM94 和 COM3 并行,SN 计数器独立。

提示:
- 在 `filter_rules.json` 里**不要**剔除任何 COM 端口
- 让所有端口的 SN/MAC/ICCID/追溯码都进入抽取
- 让时间窗口绑定(默认 300 秒)做记录聚合

如果效果不好,可考虑 v2 的多因子绑定(端口+时间+内容)。

## 四、版本管理

`device.json` 的 `version` 字段用于版本管理:

```json
{
  "version": "1.0.0",
  ...
}
```

修改规则后,务必升 version:
- **补丁**(过滤规则微调): 1.0.0 → 1.0.1
- **新增字段**: 1.0.0 → 1.1.0
- **不兼容改动**: 1.0.0 → 2.0.0

---

## 五、测试覆盖建议

至少跑通 3 种样本:

| 样本类型 | 用途 |
|---|---|
| 正常批次 | 验证基线 |
| 已知有 Bug 的批次 | 验证异常检测能力 |
| 极小批次(1~3 台) | 验证边界场景 |

---

## 六、发布流程

1. PR 提交规则 + 样本(注意样本要**脱敏**!)
2. CI 跑规则自检(必须通过)
3. 合并到 main
4. 重新打包 EXE:`python3 build.py`
5. 分发新版本

---

## 七、遇到困难?

1. 看 `README.md` 的"已知限制"章节
2. 参考 A02FG 完整规则:`agent/devices/A02FG/`
3. 联系主开发者,提供:
   - 设备型号
   - 1~2 个真实样本(.txt/.log/.db/.csv,脱敏后)
   - 你已经填好的规则文件
