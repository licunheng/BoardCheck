# 10 - SN 错绑:失败循环偷上一台设备的旧 SN(2026-08-19)

> 状态:🟢 已修复(`agent/core/extractor.py` SN 绑定改为「锚点之后优先」)
> 触发用户反馈:F16G 报告里 `209D89881970C04B3F982FF020CDF908` 被绑到 `F176XYXI5R701988899C38`,
> 而真值应属于 `F176XYXI5R701988899D20`。

## 现象

报告把 `209D...` 判为 C38 的 SN(平台 C38 的 SN 是 `389C...`),并把该 SN 同时判给 D20,
触发「SN 一值对应 2 个追溯码」的 1:1 冲突。实测 C38 的真 SN 是 `389C8988197068A43F982FF0B8DCF908`。

## 根因

设备 C38 第一次发 trace(17:52:14)失败(`error:Ret trace code`),重试;真正的成功循环
第二次发 trace 是 17:53:10,它的 SN(`389C...`)在 **17:53:13** 出现。

旧抽取逻辑为 SN 做「同串口 + 窗口内时间最近」绑定:
- C38 失败循环锚点(17:52:14)窗口内的最近 SN 是 **D20 的** `209D...`(17:51:33,差 41s),
  而 C38 自己的 SN(17:53:13)在 59s 之外;
- 于是把 D20 的 SN 偷给了 C38 → 1:1 冲突 + 平台误判。

**物理时序**:`收 :id:`(SN)是在 `发: trace code:` 之后设备回读的,所以成功循环的 SN
一定在锚点之后;失败循环的上一台设备旧 SN 恰在锚点之前。

## 修复

`agent/core/extractor.py`:
- 新增 `_nearest_after_same_port`(有 after 选最近 after,无 after 兜底最近);
- SN 绑定改用 after-优先;ICCID 仍用「就近」(设备常在发 trace 前先读卡,after-优先会把 ICCID 推到下一台)。

## 验证

对 05-27 日志重跑(修复前后):

| 追溯码 | 修复前 SN | 修复后 SN | 平台 SN |
|---|---|---|---|
| C38 | `209D...`(D20 的)✗ | `389C...` ✓ | `389C...` |
| D20 | `209D...` | `209D...` ✓ | `209D...` |
| 9FF | `AD9B...`(隔壁)✗ | `FF99...` ✓ | `FF99...` |

- 1:1 SN 冲突从 3 处降到 0;
- 05-27 summary 从 `match=59/mismatch=6` → `match=61/mismatch=4`(仅剩真实平台脏 ICCID 与平台 SN 空列);

## 教训

- **"就近"对 trace 之后才出现的字段是危险默认**:失败循环的上一台设备旧值恰在锚点之前,
  "就近"会偷过来;SN/id 应强制「锚点之后优先」。
- **同码重试是错绑温床**:同串口同码多次发 trace 时,第一次失败循环的锚点会"看到"
  前后两次循环的值;只有用「物理时序方向」才能区分。
- **质量层的 1:1 冲突是错绑的报警器**:一值对应多个追溯码,优先怀疑"就近绑定偷了邻居"。
