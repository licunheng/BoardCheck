# 16 - A02FG 多批次配置修复:追溯码前缀 + SN 日期 + MAC/ICCID 绑定(2026-08-23)

> 状态:🟢 已修复(A02FG 配置 4 处修改,EXE 已重打)
> 触发用户反馈:`F070XYXI7D0001008EEBD2` 在 7/13 板检日志里有,但核验时没有发现。与 A02SG #13 同类问题。

## 现象

用户上传 7/13 日志 + 平台 CSV,`F070XYXI7D0001008EEBD2` 报告"板检日志里没有"。实测 7/13 日志 31 条回复追溯码全部 `F070XYXI7D` 前缀,但引擎一条都抽不到(0/31)。

## 根因(4 处)

### ① trace_code 前缀硬编码 `F070XYXI8`(复现 #13)

`agent/devices/A02FG/extraction_rules.json`:
```json
"regex": "F070XYXI8[0-9A-F]{13}"
```
只匹配 `F070XYXI8**` 前缀(84/85)。实际 A02FG(F070 家族)批次前缀多变:

| 前缀 | 批次 |
|---|---|
| F070XYXI5J | 5/19 |
| F070XYXI5I | 5/18 |
| F070XYXI6I / 6M | 6/18, 6/22 |
| F070XYXI7D | **7/13** ← 用户遇到的 |
| F070XYXI84 / 85 | 8/04, 8/05 |
| F070ZHHI7K / 6N | 零星 |

**修法**:`F070XYXI8[0-9A-F]{13}` → `F070[0-9A-Z]{6}[0-9A-Z]{12}`(F070 家族常量 + 6 位变体 + 12 位尾段),覆盖全部平台 444 条 + 7/13 日志 31 条 fullmatch,且不匹配 Z047 中间码。

### ② SN 日期段硬编码 `2402608`(仅 8 月批次)

`extraction_rules.json` + `filter_rules.json` + `device.json` 三处都把 SN 前缀锁死 `FA0000014000012402608`。但 SN 日期段随生产批次变:
- 6 月批次:`FA0000014000012402606...`(如 `240260622000100041`)
- 7 月批次:`FA0000014000012402607...`
- 8 月批次:`FA0000014000012402608...`

导致:
- `keep_patterns` 把非 8 月 SN 行全丢弃(preprocessor 阶段,SN=None 的根因)
- 抽取 regex 也匹配不上

**修法**:所有 `FA0000014000012402608...` → `FA000001400001[0-9A-F]{18}`(14 + 18 = 32 位完整 SN)。

### ③ MAC 派生绑定未开启,就近绑定偷邻居

`device.json` 有 `mac_lives_in_trace_code` / `trace_code_last_8_chars_equal_mac` 但缺 `mac_derived_from_trace`。MAC 走时间窗就近:
- 慢速板检设备(ICCID→reply 间隔 68s)与下一台设备窗口重叠,就近抓到下一台的 MAC
- 实测 MAC == trace[-12:] 100%(平台 150/150 + 7/13 30/30)

**修法**:`device.json` field_constraints 加 `"mac_derived_from_trace": true, "mac_trace_suffix_len": 12`。

### ④ ICCID 就近绑定偷下一台(需 before 方向)

ICCID 在板检中段读入(回复追溯码之前)。就近绑定在慢速设备上抓到下一台的 ICCID:
- F070XYXI7D00015E11AD6D 正确 ICCID=898604A01025D0152027(锚点前 68s),被绑成 898604781025D0538580(锚点后 54s,下一台设备)

**修法**:extractor 支持 `iccid_direction` 配置(A02SG/A02EG 保持 nearest 默认),A02FG 设 `before`。

## 修改文件

1. `agent/devices/A02FG/extraction_rules.json`:
   - `trace_code.regex`: `F070XYXI8[0-9A-F]{13}` → `F070[0-9A-Z]{6}[0-9A-Z]{12}`
   - `sn.regex` / `context_anchor`: `FA0000014000012402608[0-9A-F]{11}` → `FA000001400001[0-9A-F]{18}`
   - `session_binding`: 加 `iccid_direction: before`
2. `agent/devices/A02FG/filter_rules.json`:
   - `keep_patterns` 两处 `FA0000014000012402608` → `FA000001400001`
   - `field_anchors.sn` / `field_anchors.trace_code` 同步放宽
3. `agent/devices/A02FG/device.json`:
   - `sn.pattern_in_raw` / `anchor_in_text_log` / `field_constraints.sn_format`: 放宽日期段
   - `trace_code.pattern_in_raw` / `anchor_in_text_log`: 放宽前缀
   - `field_constraints`: 加 `mac_derived_from_trace: true, mac_trace_suffix_len: 12`
4. `agent/core/extractor.py`:
   - 绑定逻辑支持 `iccid_direction`(before/nearest/after),默认 nearest 保持旧行为

## 教训

- **#13 的修复必须推广到同族全部设备**:A02SG 修了前缀,但 A02FG/A02EG 各自也有自己的硬编码变体。每个设备的「家族常量 + 批次变体段」都要扫平台 CSV 全部唯一前缀后放宽。
- **日期段是另一类「批次变体」**:SN 里的日期码(2402606/7/8)和生产批次绑定,硬编码 8 月会漏 6/7 月。凡是字段含日期/批次段,都要 `{n}` 放宽。
- **keep_patterns 与 regex 必须同步放宽**:只改抽取 regex 不改 keep_patterns,SN 行在 preprocessor 就被丢,等于没修(A02FG 这个坑踩了两次)。
- **MAC 派生绑定(按追溯码末段)比时间窗就近可靠**:有派生关系(实测 100%)就开,别依赖就近。

## 规则沉淀

- **RULE-ALL-DEVICES-PREFIX-SCAN**:同族设备(A02SG/A02EG/A02FG)都要扫平台 CSV 全部唯一前缀,家族常量 + 变体段 `{n}` 放宽,不能只修一台。
- **RULE-DATE-SEGMENT-IS-BATCH-VARIANT**:SN/字段含日期段(2402606/7/8)按批次变,regex 与 keep_patterns 必须 `{n}` 放宽,不能硬编码某月。
- **RULE-KEEP-AND-REGEX-SYNC**:放宽字段正则时 keep_patterns(可能还有 field_anchors)必须同步,否则 preprocessor 先丢。
- **RULE-MAC-DERIVED-OVER-NEAREST**:有 MAC←追溯码派生关系(实测 100%)必须开 mac_derived_from_trace,就近绑定在慢速板检+窗口重叠时偷邻居。
