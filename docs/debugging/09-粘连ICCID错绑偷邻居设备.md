# 09 - 粘连 ICCID 串导致错绑:一追溯码偷了邻居设备的 ICCID(2026-08-19)

> 状态:🟢 已修复(`agent/core/extractor.py` `_dedupe_repeated` + F16G 配置)
> 触发用户反馈:F16G 对比表中追溯码 `F176XYXI6N701988899C4D` 的 ICCID 是 `89860468152590219670`,
> 而这个 ICCID 明明属于 `F176XYXI6NDC045AD2DED7`;C4D 真值应为 `89860468152590219181`。

## 现象

对比表里 C4D 行被绑上**下一台设备 DED7 的 ICCID**,而 C4D 自己的 ICCID 在日志里其实打过:

```
F176XYXI6N701988899C4D  raw_ICCID=89860468152590219670   ← 错(DED7 的)
F176XYXI6NDC045AD2DED7  raw_ICCID=89860468152590219670   ← 对
```

平台侧 C4D 的 `4G信息` 是 `89860468152590218986` —— 也是脏值(见下)。

## 根因

### ① 上位机把 ICCID 打成「粘连串」,旧正则整体匹配失败 → 该循环无 ICCID 关键行

C4D 的最后一条测试循环(17:50:49)打印:

```
收 :ICCID:898604681525902189860468152590219181
        ├──── 89860468152590218986 ────┘ └── 0468152590219181 ──┘
              (脏前缀,非完整号)              (= 真值 89860468152590219181 缺 8986 前缀)
```

旧正则 `(8986[0-9]{15,16})(?![0-9])` 对 36 位粘连串**整体匹配失败**(因为它要求"8986+15~16位数字"后必须是边界,但后面还跟着数字)。

### ② 缺失的 ICCID 被「就近绑定」补齐 → 偷邻居

`_nearest_in_window` 在 60s 窗口内找同串口最近的一条 ICCID 关键行;
该循环没有 ICCID 行,于是把**下一台设备(DED7,17:51:42)的 ICCID** 绑给了 C4D。

### ③ 平台侧同样取了「第一个脏前缀」

平台 `4G信息 = 89860468152590218986` —— 正是粘连串的第一个号(残缺前缀)。
即平台与旧逻辑都在**取第一个**,而实测**最后一个完整号才是当前设备真值**。

## 修复

1. **引擎** `agent/core/extractor.py`:
   - `_dedupe_repeated(s, line)` 改为**扫描整行**,收集所有完整的 19-20 位 `8986` 号,返回**最后一个**;
   - `_apply_post_process(value, ext, line)` 把原始行传给去重逻辑,兼容"正则只捕获到被 `?` 截断的前缀"的情况(如 `89860468152590219?89860468152590219741`);
   - 退化逻辑保留:非 8986 字段仍按"重复前缀截断"处理。
2. **F16G 配置** `extraction_rules.json`:
   - iccid 正则由 `(8986[0-9]{15,16})(?![0-9])` 放宽为 `(8986[0-9]{15,})`(下限 16 位数字),使完整粘连串进入捕获组,交给 `sanitize_duplicates` 后处理取最后一个完整号;
   - 同步更新 `prompts.md` 已知陷阱。

> 关键取舍:粘连串的**最后一个完整号**才是真值(平台/上位机数据库存的是第一个=脏前缀)。
> 这与直觉相反,但 06-23 日志 9 处粘连串全部验证成立。

## 验证

对 06-23 日志重跑(修复前后):

| 追溯码 | 修复前 raw ICCID | 修复后 raw ICCID |
|---|---|---|
| `...C4D` | `89860468152590219670`(偷 DED7 的)✗ | `89860468152590219181` ✓ |
| `...DED7` | `89860468152590219670` | `89860468152590219670` ✓(不变) |
| `...9C8/B02/BBE/BC2/CCA/D4E/D7D` | 缺失或偷邻居 | 各自真值 ✓ |

- 原 4 条缺失 ICCID 全部补齐,1:1 冲突从 5 处降到 2 处(仅剩真实 SN 跨串口歧义);
- 新增回归测试(`tests/test_device_generation_fixes.py::test_dedupe_repeated_glued_iccid` / `test_iccid_regex_captures_glued_run`),全部通过;
- A02EG(不依赖 8986 粘连去重)回归 48/48 不变。

## 教训

- **"就近绑定"缺值时的兜底会偷邻居**:字段缺失 ≠ 不要绑定,而是会绑到窗口内最近的其他设备值。**必须保证每字段先有值,再谈就近**;宁可该条标记缺失,也不要抓邻居的。
- **脏值的形态要先看清再定"取哪个"**:粘连串里"第一个号"是脏前缀、**最后一个才是真值**——平台侧同样存了脏前缀,说明"取第一个"是共性错误,不能顺着错下去。
- **正则下限要能吃到坏数据**:`{15,16}(?![0-9])` 这种"到边界就停"的正则,遇到粘连串整体失败 → 字段缺失 → 触发偷邻居。宁可放宽捕获再由后处理归一,也不能让正则静默失配。
- **去重后处理要看到原始行**:只对捕获值操作,遇"首段被 `?` 截断"会拿到残前缀;整行扫描才能兜住所有粘连形态。
