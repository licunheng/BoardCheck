## 关键判断:A02FG 的裸追溯码是「中间码」,绝不能加

A02FG 日志中裸 `追溯码:` 行全部是 **Z047 开头**(1075 条),回复追溯码是 **F070 开头**(64 条):

```
11:07:45 740 | COM76:追溯码:Z047XYXI85DC045A6383BD   ← 中间码(MAC 读取后生成)
08:03:03 440 | COM94:回复追溯码:F070XYXI85000199292D10  ← 最终追溯码(平台真值)
```

平台 CSV 追溯码全是 `F070XYXI84`(86)/`F070XYXI85`(64),**没有 Z047**。

**为什么不能像 A02SG 那样加裸形态**:
- A02SG:裸 `追溯码:F068XYXI6H...` 前缀 = 回复 `F068XYXI6H...` 前缀 → **同一个码的两种时机** → 要加
- A02FG:裸 `追溯码:Z047...` 前缀 ≠ 回复 `F070...` 前缀 → **两套不同的码** → 加了会把中间码当最终码,平台比对全错

**判断规则:裸追溯码前缀与回复追溯码前缀一致才加裸形态;不一致说明裸形态是中间码,必须排除。**

## 设备配置审计检查清单(新设备/配置维护必查)

1. **追溯码形态**:裸与回复前缀是否一致?
   - 一致 → 同一码双形态 → keep_patterns + regex 都加裸形态
   - 不一致 → 裸形态是中间码 → **只匹配回复形态**,绝不加裸
2. **追溯码前缀**:扫平台 CSV 全部唯一前缀,家族常量保留 + 变体段 `{n}` 放宽
3. **窗口**:板检耗时分布必须 < 窗口;同族设备统一(300s 覆盖 5 分钟)
4. **SN 方向**:SN 是发指令(before)还是读回(after)?用 `sn_direction` 配置
5. **ICCID 格式**:hex 还是纯数字?hex 必须有 `[0-9A-Fa-f]` 收集 + sanitize,纯数字用 `[0-9]`

## 规则沉淀

- **RULE-BARE-TRACE-PREFIX-CHECK**:裸追溯码前缀与回复追溯码前缀**一致**才加裸形态;
  不一致(如 A02FG Z047 vs F070)是中间码,必须排除。
- **RULE-WINDOW-BOARD-TIME**:窗口必须覆盖板检耗时分布(最大档 < 窗口),不能只看平均。
