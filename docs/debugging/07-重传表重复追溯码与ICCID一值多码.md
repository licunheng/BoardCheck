# 07 - 重传表大量重复追溯码 + ICCID 一值多码(2026-08-16)

> 状态:🟢 已修复(数据质量层 `agent/core/quality.py`)

## 现象

11:57 生成的 F16G 重传表 `重传数据_F16G_20260816_115737.csv`:
**61 行,但去重后只有 14 个真实追溯码** —— 47 行(77%)是重复;且重复里夹着错绑:

- 同一追溯码 → 多个 SN(2 组,`...899C4D` 绑了 3 个不同 SN);
- 同一追溯码 → 多个 ICCID(3 组);
- 同一 ICCID → 多个追溯码(2 组,ICCID `...9445` 同时属于两台);
- ICCID 被截断(19 位,3 条)。

## 根因

流水线两处空白:
1. **无去重环节**:`comparator` 直接遍历 `raw_records`;而抽取器"每命中一条 trace code 行就建一条记录",一台设备多份痕迹(多循环 + 多形态)直接炸出几十条。
2. **无权威值仲裁 / 无唯一性校验**:SN/ICCID 靠"同串口+时间最近"绑,多串口并行 + 重试交错下串台;抽完不做任何跨字段一致性校验,错绑直接进交付物。

## 修复

新增**数据质量层** `agent/core/quality.py`,在抽取后、比对前执行(纯确定性、秒级):

1. **按追溯码归一去重**:trace_code(大写)为唯一主键,同码只留一条;
2. **组内权威值仲裁**:SN/MAC/ICCID 取**众数**;组内出现多个不同值 → 标记低置信度 + 记录分歧,不静默选一个;
3. **跨设备 1:1 唯一性硬校验**:建字段→追溯码反向索引,一值对应多个追溯码即判错绑、标记;
4. **ICCID 长度校验**(默认 19~20 位,可读 `field_constraints.iccid_length`);
5. **质量报告**(去重 N / 冲突 M / 截断 K)写入日志 + AI 报告 + 前端。

同时比对器 `_build_row` 的字段匹配升级为 `field_equivalent`:精确相等 → 平台值嵌入日志值(头/尾码包裹)判一致。

## 验证

对 F16G 重跑:1234 条抽取 → 去重剩 55 条;之前 134/134 全不一致的假结果消失,转为 54 一致 + 1 不一致。

## 教训

- 核心四字段(SN/MAC/ICCID/追溯码)**必须一一对应**,这是硬不变量;任何一对多/多对一冲突都要确定性拦下,不能依赖 LLM。
- "就近绑定"是启发式,会错绑;**必须用派生关系 + 唯一性校验兜底**。
