# 14 - A02SG SN 误判(时序与 F16G 相反)+ hex ICCID 被 8986 子串截断(2026-08-23)

> 状态:🟢 已修复
> 触发用户反馈:
> 1. `F068XYXI6I00018B632069` 正确 SN 是 `...000100020`,被误判成 `...000100019`
> 2. ICCID `898604781025D0538986`(20 位 hex)被误判成 `898604781025D05`(截断)

## 问题一:SN 误判——绑定方向设备差异

### 现象

6/18 日志中 `F068XYXI6I00018B632069`(COM94, 08:27:35 回复追溯码):
- 正确 SN = `FA000001400001240260618000100020`(08:27:18 发 SN 指令)
- 系统误绑 = `...000100019`(08:28:03 发 SN 指令,下一台设备)

### 根因

A02SG 与 F16G 的 **SN 时序相反**:

| 设备 | SN 出现时机 | 位置相对锚点 |
|---|---|---|
| F16G | `收 :id:`(设备回读) | **锚点之后**(trace code 读回后) |
| A02SG/A02EG/A02FG | `发:568121440200`(上位机发指令) | **锚点之前**(板检开始时) |

`extractor.py` 旧代码对所有设备统一用 `_nearest_after_same_port`(锚点后优先,
#10 为 F16G 加的修复)。对 A02SG 造成:
- 本设备 SN(020, 锚点前 17s)被跳过
- 下一台设备 SN(019, 锚点后 28s)被选中 → 误判

### 修复

`session_binding.sn_direction` 配置化,`extractor.py` 读取并选择绑定方向:

```json
"session_binding": {
    "window_seconds": 300,
    "sn_direction": "before"
}
```

- `before`: 锚点前最近(SN 指令在板检开始发)→ A02SG/A02EG/A02FG
- `after`: 锚点后最近(SN 在 trace 后读回)→ F16G(默认,保持 #10 修复)
- `nearest`: 就近

新增 `_nearest_before_same_port`(锚点前最近,无则就近兜底)。

### 验证

`F068XYXI6I00018B632069` 现在正确绑定 SN=`...000100020`。

## 问题二:hex ICCID 被 8986 子串截断

### 现象

A02SG 的 ICCID 是 **hex 字符串**(含 `D` 等字符),如 `898604781025D0538986`(20 位)。
`_dedupe_repeated`(sanitize_duplicates 后处理)把它截断成 `898604781025D053`。

### 根因

`_dedupe_repeated` 两处假设都只适用于**纯数字**粘连(F16G 场景):
1. `src[j].isdigit()` 收集——遇到 `D` 就停,收集不全
2. 退化逻辑 `s[first:second]`(第一个 8986 到第二个 8986 之间)——把 hex 号内部天然
   的 `8986` 子串(`...D0538986` 的末尾)误判为"重复开头",截断

### 修复

`_dedupe_repeated`:
1. 收集字符从 `isdigit()` 改为 `in "0123456789ABCDEFabcdef"`(支持 hex)
2. 长度 >= 19 即视为完整号候选(取前 20 位),返回最后一个
3. 找不到完整号时**原样返回 s**,不再用 `s[first:second]` 截断

### 验证

- `898604781025D0538986` → 原样保留(20 位)✓
- 纯数字粘连回归不变:`898604681525902189860468152590219181` → `89860468152590219181` ✓
- 6/18 日志 22 个含 D 的 ICCID 全部 20 位完整,0 长度异常 ✓

## 附带修复:窗口 120→300

6/18 有一台设备板检耗时 129s(08:53:49 SN → 08:55:58 回复追溯码),超出 120s 窗口,
SN 绑定不到。A02SG/A02EG 窗口统一扩到 300(与 A02FG 一致)。

## 教训

- **绑定方向不是全局默认,是设备物理时序**:SN 在锚点前(发指令)还是锚点后(读回),
  取决于设备固件实现。F16G 的 after 修复不能无差别套到 A02SG。新设备接入必须先确认
  SN/MAC/ICCID 相对 trace 锚点的时序方向。
- **hex 字段的"去重"必须有 hex 意识**:`_dedupe_repeated` 的 `8986` marker 对 hex ICCID
  是危险的——ICCID 内部可能天然含 `8986`。识别"完整号"必须按字段格式(数字/hex)。
- **窗口必须覆盖最慢板检**:120s 不够时(实测 129s),绑定缺失。同族设备窗口应统一。

## 规则沉淀

- **RULE-BINDING-DIRECTION-IS-DEVICE-SPECIFIC**:SN 绑定方向由设备配置
  `session_binding.sn_direction` 决定(after=读回型 F16G, before=指令型 A02SG/A02EG/A02FG),
  禁止全局硬编码。
- **RULE-HEX-FIELD-DEDUPE**:对 hex 字段(如 A02SG ICCID)做粘连去重必须按 hex 字符收集,
  退化逻辑禁止用 `s[first:second]` 截断(会误判内部子串)。
- **RULE-WINDOW-COVERS-SLOWEST**:时间窗口须大于最慢板检耗时,同族设备窗口统一(300s)。
