# 08 - F16G MAC 大面积错绑 + LLM 复核空转(2026-08-16)

> 状态:🔴 已定位根因、已出方案,待实施。
> 这是本次暴露出的**最关键问题**,方案沉淀在 `openspec/changes/improve-rule-generation-and-llm-observability/`。

## 现象

勾选「LLM 复核 + 独立抽取交叉验证」后跑 F16G,对比表里 **34 条 MAC 明显误判**(标 ✗),且报告里 LLM 复核一行全是 0:

```
独立抽取:大模型分块抽取 0 条,与正则对账发现 0 处分歧,其中 0 处修正。
比对复核:复核 0 条不一致记录,判定 真实问题 0 / 绑定错误 0 / 批次不同 0 / 误报 0。
```

数据质量层同时报:**1234 条抽取 → 去重 1068 → 剩 166,但 25 处一一对应冲突**。

## 环境

- 设备 F16G,双串口 COM77/COM79 并行板检;
- 原始日志 `Info-2026-06-23 -f16g.txt`(2 万行);
- LLM 走代理,后端是 **deepseek 类推理模型**(max_tokens 被 thinking 耗尽)。

## 根因(四个叠加)

### ① trace_code 有 3 种形态,全被当锚点 → 同设备 3 个锚点

日志里一条 trace code 会以 3 种行出现,而 regex `trace\s*code:\s*([A-Za-z0-9]+)` 三种全命中:

```
268  COM77:收 :Ret trace code            ← 命中?(经核对其实被过滤)
270  COM77:发: trace code:F176XYXI6N701988899BBD   ✓ 锚点1
279  COM77:收 :trace code:F176XYXI6N701988899BBD    ✓ 锚点2
281  COM77:trace code:F176XYXI6N701988899BBD        ✓ 锚点3
```

实测:**同一(追溯码,串口)出现 3 次的有 176 组**。`extract_from_text_log` 对每个 trace_code 锚点都建一条记录 → 同一设备被拆成 3 条,再各自"就近抓 mac"。

### ② 双串口交错 + 就近绑定 → 抓到隔壁设备的 mac

时间轴上 COM77 与 COM79 的循环交错,3 个锚点里有的离隔壁设备的 mac 更近:

```
177  16:00:56  COM77:收 :mac:701988899BBDF2      ← COM77 设备的 mac
180  16:00:56  COM79:收 :mac:701988899BA6DB      ← COM79 设备的 mac
245  16:01:20  COM79:发: trace code:...BA6       ← COM79 锚点A(离 180 近,抓对)
270  16:01:23  COM77:发: trace code:...BBD       ← COM77 锚点
279/281 COM77:收:trace code:...BBD               ← COM77 锚点B/C(也可能抓错)
```

**34 条 MAC ✗ 全部实测为"rawMAC 前12位 ≠ 追溯码末12位" → 真错绑**,0 条是格式误判。

### ③ MAC 派生判据用错(末 8 位),且被配置关掉

平台实测:**`蓝牙mac` = 追溯码后 12 位**(100% 成立):

| 追溯码 | 蓝牙mac | 后12位相等 |
|--------|---------|-----------|
| F176XYXI6O**701988899D47** | 701988899D47 | ✓ |

但日志 mac 行是 **14 位 = 后12位 + 2位尾码**(`...9C568C`,尾码 8C)。
代码里 `_mac_matches_trace` / `_find_mac_by_trace_suffix` 用的是 **末 8 位** 判据——14 位 mac 的末 8 位含尾码,永远 ≠ 追溯码末 8 位 → **确定性校正永久失效**;而 `device.json` 里 `trace_code_last_8_chars_equal_mac=false` 又把这层校验关了。

### ④ LLM 复核空转(直接兜底失败)

`llm_review.extract_records_with_llm` 按 200 行切块逐块调 LLM,但**推理模型后端把 token 全耗在 thinking、输出 0 条可解析内容**,每个 chunk 都是 0 条 → 交叉验证没抽出一台设备,错绑 mac 自然无人纠正。

## 修复(方案,见 openspec)

分四步(确定性修复优先、不依赖 LLM):

1. **MAC 派生判据改末 12 位**,并恢复为硬约束;
2. **trace_code 锚点只取"发:"形态**(权威、唯一),杜绝一设备三锚点;
3. **绑定窗口收窄**(300s→60s)+ 先用派生关系筛 mac 再兜底时间窗;
4. **LLM 复核加"空转探针"**:chunk 0 条 / 解析失败计数,全 0 则明确告警"复核未生效"而非显示"分歧 0"。

详见 `openspec/changes/improve-rule-generation-and-llm-observability/proposal.md`。

## 验证方法

对 `Info-2026-06-23 -f16g.txt` 重跑,断言:
- MAC ✗ 数量从 34 降到 ≈0(错绑消除);
- trace_code 锚点数 ≈ 真实设备数(不再 ×3);
- 质量层 `conflicts` 从 25 降到 0;
- LLM 复核 chunk 不再全 0(或明确报"复核不可用")。

## 教训

- **派生关系是设备固化的"硬事实",是绑定/校正的最强锚点**,比"时间就近"可靠得多——能用派生就优先用派生。
- **多形态行的锚点要去重**:同一个逻辑字段(这里 trace code)在日志里出现多次时,要指定"以哪种形态为准",否则一设备多锚点直接炸开绑定。
- **LLM 兜底绝不能静默失效**:它跑没跑出东西,必须能被用户看见。
